# git4ai — 被 git4ai 约束的 AI 使用指南

> 解决「AI 提交一堆又糙又长的 commit、message 两三个字、改了代码却不同步文档」的失控问题。
> git4ai 是强加在你提交链路上的**唯一可靠约束点**：提交前强制校验，违规就拒绝，直到你改对为止。
> 本技能把它的三条规范变成你每次 commit 前的**默认自查动作**，让你少被拒、一次过。

## 触发条件

- **触发**：任何要执行 `git commit` 的时机 —— 新建代码、修改代码、修 bug、重构、AI 生成/补全、提交被 git4ai 拒绝后重试。
- **不触发**：仅 `git add` / `git status` / `git log` / `git diff` / `git push` 等非 commit 操作(不校验)。
- 一旦要 commit，先走完下面的【提交前自查】，再真正 commit。

## 三条铁律（git4ai 的检查项）

git4ai 在你 `git commit` 时会做三件事，**任一不满足就拒绝**(exit 1,不动你的暂存区):

| # | 检查 | 门槛 | 豁免 |
|---|---|---|---|
| 1 | 变更行数(暂存区新增+删除) | **≤ 50 行** | `.md`、`tests/` 下文件、`test_*` / `*_test.*`、隐藏文件(`.` 开头) |
| 2 | commit message 去空白后字数 | **≥ 300 字**(Unicode,中文按字计) | 无 |
| 3 | 代码变更须带**同目录同名 `.spec.md`** | 本次变更集合内必须有 | `.md`、测试、隐藏文件；**首次 commit(仓库无 HEAD)** |

一句话记忆:**行数少 / 话要满 / 代码必带 spec**。

## 核心原则

1. **先自查再提交**：把三条校验当成你写 commit 前的 checklist，不依赖 git4ai 帮你拦。
2. **小步提交**：一次改动量 ≤50 行、一次一个逻辑点、一次一个 commit —— 这既是规则也是最佳实践。
3. **message 说人话**：≥300 字 = 覆盖「为什么改 / 怎么改 / 风险与验证」，不是凑字数堆废话。
4. **代码与 spec 同生共死**：改代码，`同目录同名 .spec.md` 必须在同一个 commit 里跟着变。
5. **被拒不可怕**：git4ai 只拒绝不改状态，照它给的修复建议改到通过再 commit，坚决不用 `--no-verify`。

## 提交前自查（5 步）

> 每次要 commit 时按序执行，全部通过才执行 `git commit`。

### Step 1 数行数
- 暂存区变更 = `git diff --cached --numstat`,把**非豁免文件**的 `新增 + 删除` 加起来。
- **超 50 行 → 拆**。拆成多个逻辑独立的 `≤50 行` 小提交，先核心逻辑后配套，一个机制一个 commit。

### Step 2 凑合 message
- 用 `-m` 提供;去空白必须 `≥ 300` 字。
- 三段式结构:【为什么改】→【怎么改】→【风险与验证】。
- 不够长 → 主动补充:动机、影响模块、边界、验证方式,别停在一个短句上。

### Step 3 检查 spec 同步
- 本次每个**代码文件**(非 `.md`、非测试、非隐藏)→ 必须有对应的 `同目录同名 .spec.md`,且在**同一个 commit** 里。
  - `src/foo.py` → 需要 `src/foo.spec.md`;`win/main.go` → `win/main.spec.md`;`win/install.bat` → `win/install.spec.md`。
- 新增代码首次出现时,按 spec-slave 模板同时新建该 `.spec.md`。

### Step 4 扫一眼命令
- 关闭任何 `--no-verify` / `-n`(git4ai 直接拒绝)。
- 确认全局参数(`-C 目录`)指向了正确的仓库。

### Step 5 提交并验证
- `git commit -m "完整 ≥300 字 message"`。
- 若被拒 → 读 stderr 的结构化建议,回到对应 Step 修,再重新 commit(它不会破坏你的修改)。

## 提示词模板速查

| 场景 | 提示词 |
|---|---|
| 自查行数 | 「列出本次暂存区所有非豁免文件，逐个算新增+删除行数，确认总数 ≤50；超了就把改动拆成逻辑独立的小提交」 |
| 写满 message | 「为这次改动写 commit message：为什么改 / 怎么改 / 风险与验证，去空白 ≥300 字，中文」 |
| 同生 spec | 「列出本次变更的每个代码文件，并确认同目录同名 .spec.md 也在本次变更里；缺的按 spec-slave 模板补齐」 |
| 被拒后重提 | 「git4ai 拒绝了，把 stderr 里每条违规对应的修复点列出来逐一修，再重新 commit，不要 --no-verify」 |
| 大文件入库 | 「这是新增一个完整模块，单文件必然超 50 行无法拆分——请向用户说明绕过的原因（直接调真实 git），并征得同意」 |

## 附录 A：合规 message 模板(≥300 字)

```text
<一句话主题>:
动机与背景:<为什么要加/改?解决什么问题?>
实现方式:<改了哪些文件?核心逻辑/接口怎么变的?>
关键决策:<有取舍时,为什么这么选?>
风险与验证:<可能影响哪些模块/功能?有没有测试和边界用例?在哪验证过?>
```

## 附录 B：.spec.md 模板（spec-slave 规范,与代码双同步）

```markdown
# <文件名>.spec.md

> 本文件与同名源码**双向同步**:改代码必须同步本文件,改本文件必须落实到代码。

## 用途
## 对外接口
| 名称 | 签名/格式 | 说明 |
|---|---|---|
## 关键行为与约束
## 边界与异常用例(corner cases)
| 用例名 | 输入 | 预期行为/结果 |
|---|---|---|
## 依赖与影响面
## 变更记录
| 日期 | 版本 | 变更摘要 | 关联 commit |
|---|---|---|---|
```

## 附录 C：常见被拒场景 → 处置

| 被拒场景 | stderr 指向 | 处置 |
|---|---|---|
| 变更行数超限 | 「变更行数超限：本次共 N 行,超限文件明细...建议拆分」 | 拆成多个 ≤50 行小提交 |
| message 过短 | 「当前 X 字(去空白),要求 ≥300,还差 Y 字」 | 补足三段式,别凑字数 |
| 缺少 spec 同步 | 「代码文件 → 需要 .spec.md,且与代码同一次提交」 | 补 `.spec.md` 并与代码同 commit |

## 一句话总结

git4ai 不是来卡你的,是来防止你留下「长改动 + 短说明 + 无文档」的失控 patch 的。
把它三条规范(≤50 行、≥300 字、带 spec)当成你每次 commit 的默认习惯,**先自查再提交,一次过**;真遇到"单文件新模块"这种合法超限,向用户说明后按核准方式入库。
